# release

Выпускает релиз: считает следующую версию, бампает `version.py`, делает коммит и ставит аннотированный тег.

Заменяет ручной чек-лист из технической документации (`docs/developer_guide.html`, раздел «Версионирование и релиз») («поменять версию → закоммитить → `git tag -a` → `git push --follow-tags`). Смысл не в том, чтобы не печатать номер руками, а в теге: из первых одиннадцати релизов проекта пять (08.6–08.10) остались без тегов — проседает именно этот шаг.

## Что делает

1. Читает текущую версию из `version.py` и считает следующую по CalVer: тот же месяц — номер `+1`, новый месяц — сброс на `1`.
2. Переписывает `__version__`.
3. Коммитит **то, что лежит в индексе**, плюс `version.py`, с сообщением `Release <версия>: <описание>`.
4. Ставит аннотированный тег `v<версия>` с сообщением `Release <версия>`.
5. По флагу `--push` отправляет коммит вместе с тегом.

Сам скрипт в индекс ничего не добавляет, кроме `version.py`: что войдёт в релиз, решает `git add` до запуска — так релизный коммит не утащит случайный файл из рабочего дерева.

## Требования

- Python 3.11+, `git` в `PATH`.
- Запуск из репозитория проекта (скрипт работает относительно своего расположения, так что из какой папки вызывать — неважно).

## Запуск

```powershell
git add .                                        # решаешь, что входит в релиз
python scripts/release.py "week activity strip"
```

Вывод:

```
[RELEASE] версия  2026.08.11 -> 2026.09.1
[RELEASE] коммит  Release 2026.09.1: week activity strip
[RELEASE] файлы   version.py + в индексе: 11
[RELEASE]           README.md
[RELEASE]           ...
[RELEASE] тег     v2026.09.1 (аннотированный)
[RELEASE] пуш     нет (--push выключен)
[RELEASE] готово: 9e31b0a Release 2026.09.1: week activity strip
[RELEASE] не забудь отправить: git push --follow-tags
```

Описание необязательно: без него заголовок будет просто `Release 2026.09.1` (в истории такие есть).

## Флаги

| Флаг | Что делает |
|---|---|
| `--dry-run` | Печатает план и выходит, ничего не меняя |
| `--body "текст"` | Тело коммита под заголовком (можно многострочное) |
| `--push` | После тега выполняет `git push --follow-tags` |
| `--version-only` | Разрешает релиз с пустым индексом: в коммите будет только бамп версии |

## Проверки перед записью

Скрипт останавливается до первой записи, если:

- **`__version__` отличается от версии в `HEAD`** — похоже, версию бампнули руками; иначе получился бы двойной инкремент. Сбрось правку: `git checkout -- version.py`. Прочие изменения в `version.py` (например, правка докстринга) релизу не мешают и войдут в коммит.
- **тег `v<версия>` уже существует** — версия уже выпускалась.
- **индекс пуст** и не передан `--version-only` — выпускать нечего.

Если коммит всё-таки не прошёл (например, его отклонил pre-commit хук), скрипт возвращает `version.py` в исходное состояние и убирает его из индекса; остальной индекс остаётся как был. Если упал только тег, коммит остаётся в истории — скрипт печатает готовую команду `git tag -a ...`, чтобы дотегать вручную.

## Откат

Пока ничего не отправлено в удалённый репозиторий:

```powershell
git tag -d v2026.09.1
git reset --soft HEAD~1     # снять релизный коммит, изменения останутся в индексе
git checkout -- version.py  # вернуть версию
```

## Почему не метод в `version.py`

`version.py` импортируется приложением и попадает в сборку PyInstaller, где нет ни репозитория, ни `git` — метод релиза был бы там кодом, который не может выполниться там, где живёт. В `version.py` версия остаётся тем, чем была: источником истины, который читают.
