Окружение и запуск

Ядро (мониторинг сессий и ввода, виджет, отчёты) работает на стандартной библиотеке + ctypes. Внешние пакеты нужны только для значка в трее — pystray и Pillow (requirements.txt). Без них приложение работает, но значка нет: кнопка «свернуть в трей» откатывается к сворачиванию до заголовка (ActivityWidget._toggle_minimize: прячутся разделитель и тело, тулбар выезжает при наведении — см. toolbar_reveal.py), а в консоль выводится подсказка с командой установки для нужного интерпретатора.

Рекомендуемый способ — отдельное виртуальное окружение проекта, чтобы приложение всегда запускалось своим интерпретатором со своими зависимостями:

py -3.12 -m venv .venv
.venv\Scripts\python -m pip install -r requirements.txt
.venv\Scripts\python main.py          # или start.bat

Тесты — pytest, все в папке tests/: python -m pytest tests. Tkinter в тестах не поднимается: тестируется чистая логика (интервалы, раскладки, схемы, разбор комбинаций).

Архитектура и потоки

main.py переводит stdout/stderr в UTF-8 (bootstrap.setup_console(): логи русские и со стрелками, а под перенаправленным выводом Windows подставляет cp1251 и print падает с UnicodeEncodeError; ошибки кодирования заменяются на «?»), подключает пользовательский конфиг (bootstrap.setup_user_config() — до любых импортов, читающих config), затем запускает монитор сессий в daemon-потоке SessionMonitor, а в главном потоке — ядро UI (modules.widget.App). Если в окне-конфигураторе выключены все строки тела (is_widget_enabled()), окно стартует спрятанным в трей — мини-виджеты и трей работают как обычно; без трея окно показывается всегда, иначе приложение нельзя было бы ни настроить, ни закрыть.

Ключевые приёмы:

  • колбэки вместо импортов — events_monitor получает log_event колбэком, чтобы не было кольца импортов;
  • хуки только присваивают time.monotonic() и вызывают CallNextHookEx; весь I/O — в timer-потоке. Атомарность присваиваний float/str между потоками обеспечивает GIL;
  • остановка потоков через threading.Event / request_stop();
  • состояние дня защищено state_lock, которым владеет session.py.

Пакет modules/session_monitor/ собран слоями снизу вверх, импорты строго в одну сторону; внешние потребители импортируют всё из фасада modules.session_monitor, не зная раскладки:

state_store   — state.json и схема записи дня (v2), сериализация интервалов
journal       — строки лога дня: сборка и разбор (чистый текст, без I/O)
activity      — пересчёт активного времени и таймлайна из сырых интервалов
day_report    — мост day_state ↔ дневной JSON-отчёт (запись и чтение прошедших дней)
session       — владелец рантайма (session_start_time, state_lock) и жизненный цикл:
                start/end/checkpoint/recover, log_event
checkpoint    — фоновый таймер промежуточного сохранения
stats         — get_current_stats для виджета
manual_time   — ручное добавление/удаление активного времени
win_events    — WTS-подписка, скрытое окно, цикл сообщений, main()

Модель активного времени

События

В лог дня пишутся события: LOGON, LOGOFF, LOCK, UNLOCK, IDLE (зафиксированный период простоя), MANUAL_ADD_START/MANUAL_ADD_END (ручные диапазоны), SESSION_RECOVERED (сессия дотянута после сбоя).

Схема v2: сырые интервалы

Программа записывает не «активно/неактивно», посчитанное по таймауту, а сырые интервалы: периоды включённой сессии sessions ([start, end]) и гэпы простоя ввода idle ([from, to], без вычета таймаута). Активное время — проекция от них с текущим таймаутом для дня недели этой даты (utility.get_input_timeout по INPUT_ACTIVITY_TIMEOUT_BY_DAY; 0 = гэпы этого дня не вычитаются), вычисляемая в момент чтения/записи. Поэтому изменение таймаута пересчитывает весь день, включая прошедшую часть. Старые записи (v1) читаются как раньше: ensure_v2 сохраняет накопленное active_seconds как legacy_base_seconds (за вычетом ручного времени, которое пересчитывается из лога заново).

Ядро — modules/activity_intervals.py, чистые функции без I/O:

неактивность гэпа   = [from + timeout, to]      (None, если гэп короче таймаута)
активное за день    = Σ длительность сессий − Σ неактивность
                      (пересечения обрезаются границами суток [00:00, следующая полночь))

Таймаут — разовая «фора», сдвигающая начало гэпа, поэтому переход через полночь обрабатывается корректно. Пересчёт точен для таймаутов ≥ MIN_IDLE_GAP_SECONDS. Тот же код раскладывает таймлайн дня для круга и полосы «Таймлайн».

Две нормы

Единая точка расчёта — utility.py: get_work_hours(date) (присутствие: WORK_HOURS_BY_DAY с переопределениями из календаря work_calendar.py), get_break_hours(date), get_activity_norm_hours(date) = рабочие часы − перерыв, не ниже нуля; в нерабочий день перерыв не вычитается. Присутствие красится по RECOMMENDED_WORK_TIME_THRESHOLD/MIN_WORK_TIME_THRESHOLD, активность — по RECOMMENDED_ACTIVITY_THRESHOLD/MIN_ACTIVITY_THRESHOLD.

Свободное время

бюджет_rec  = присутствие − норма_активности × RECOMMENDED_ACTIVITY_THRESHOLD / 100
бюджет_min  = присутствие − норма_активности × MIN_ACTIVITY_THRESHOLD / 100
потрачено   = full_day_seconds − active_seconds
остаток     = бюджет_rec − потрачено        (не подрезается нулём, показывается со знаком)

Цвет — по остатку до рекомендуемой нормы (зелёный / жёлтый при остатке ≤ FREE_TIME_WARNING_PERCENT% бюджета / красный при ≤ 0). Кольцо «Свободное время» за 100% берёт бюджет_min, чтобы пустеть непрерывно; при остатке ниже минимальной нормы красным становится трек.

Достижение нормы активности

Прогноз = now + (норма_активности × порог − active_seconds); после взятия порога — фактический момент, вычисленный по тем же интервалам дня, и дальше не меняется. None → «—» (нерабочий день или нулевая норма). Тесты — tests/test_recommended_eta.py.

Усечение процентов

utility.truncate_percent: дробная часть отбрасывается, и с порогами сравнивается то же показанное число — иначе округление вверх давало «80%» жёлтым. Правило действует везде: тело и заголовок виджета, мини-виджеты, тепловая карта, отчёт за период (tests/test_percent_display.py).

Файлы данных и схемы

Всё в LOG_DIR = ~/active_time/. Чтение и запись JSON — через modules/json_file.py: отсутствующий или битый файл читается как «данных нет» (read_json → None, тип проверяет вызывающий), запись атомарная — .tmp + os.replace (write_json_atomic).

state.json

Словарь «ключ-дата YYYY-MM-DD → запись дня». Хранит только сегодня и будущие дни: прошедшие вычищает cleanup_old_days после записи отчёта (кроме случая кросс-полуночной незавершённой сессии), и источником истины для них становится дневной отчёт.

{
  "2026-09-11": {
    "active_seconds": 0,        "session_count": 0,
    "first_login": null,        "last_logout": null,
    "sessions": [{"start": "YYYY-MM-DD HH:MM:SS", "end": "..."}],
    "idle":     [{"from":  "YYYY-MM-DD HH:MM:SS", "to":  "..."}],
    "legacy_base_seconds": 0,   "log_entries": ["..."]
  }
}

Открытая сессия персистится на каждом checkpoint (CHECKPOINT_INTERVAL); при следующем запуске незакрытые из-за сбоя сессии дотягиваются — в лог добавляется SESSION_RECOVERED. При жёстком сбое теряется не более одного интервала checkpoint.

Дневной отчёт <username>_dd.mm.yyyy.json

Формирует modules/report.py (REPORT_JSON_VERSION = 2):

Ручные диапазоны на сегодня и будущее пишутся в state.json; на прошедшие даты — прямо в отчёт (он же создаётся, если активности за день не было). Читают отчёты все окна отчётов, тепловая карта и недельная полоса.

widgets.json

Плоский список записей мини-виджетов: {"id", "type", "x", "y", "opts", "enabled"}. Выключенный виджет не рисуется, но запись с настройками и позицией остаётся (widget_store.py, manager.py).

tray.json

{"tooltip_metric": "<ключ каталога>"} — метрика в подсказке значка трея; пустая строка — не показывать, нет файла или неизвестный ключ — activity. Меняется из контекстного меню значка, как настройки мини-виджетов — из их меню (widget/tray.py).

work_calendar.json

{"YYYY-MM-DD": {"hours": float|null, "note": str}}. hours: ключа нет или null — действует расписание; 0 — выходной; > 0 — переопределённый лимит. Модуль work_calendar.py держит кэш в памяти и не зависит от utility (тот импортирует календарь).

config.py

Пользовательская копия конфига — см. Конфигурация. Ещё в LOG_DIR лежит сгенерированный WAV звукового уведомления (widget/notification.py).

Мониторинг сессий

Скрытое окно + WTSRegisterSessionNotification — единственный способ узнать о LOCK/UNLOCK/LOGON/LOGOFF без прав администратора. win_events.py регистрирует класс окна (WNDCLASSW, WNDPROC из winapi.py), крутит цикл сообщений и транслирует WM_WTSSESSION_CHANGE в операции жизненного цикла из session.py: start_session / end_session / log_event. Остановка — request_stop() посылает WM_QUIT.

Мониторинг ввода

modules/events_monitor.py ставит WH_KEYBOARD_LL и WH_MOUSE_LL в собственном потоке. Колбэк хука только запоминает time.monotonic() и источник (движение мыши учитывается по config.TRACK_MOUSE_MOVE, читается динамически — применяется на лету) и передаёт событие дальше.

Timer-поток раз в секунду сравнивает момент последнего учтённого ввода с текущим: пауза ≥ MIN_IDLE_GAP_SECONDS (5 с, constants.py) по возвращении пользователя замыкается в сырой гэп [from, to] и регистрируется как событие IDLE. Конвертация monotonic → wall-clock идёт через якорь, зафиксированный на старте сессии. При блокировке экрана ввод игнорируется, открытый гэп финализируется. На подсчёт количества сессий это не влияет.

Закрытый гэп виден сразу. В state.json гэп попадает только на ближайшем checkpoint. Живая статистика (stats.get_current_stats) читает state.json, поэтому дополнительно подмешивает гэпы, которые уже закрылись, но ещё не сохранены — events_monitor.peek_idle_gaps(). Без этого простой, только что закончившийся, на минуту исчезал бы из процента активности и с круга «Таймлайн дня» (tests/test_stats_pending_idle.py).

Обратный отсчёт для заголовка и мини-виджета «Счётчик активности» считается здесь же по сегодняшнему таймауту (get_input_timeout(today); 0 — отсчёта сегодня нет) — это про «сейчас», а не про запекание истории. Нули во все дни (utility.input_monitoring_enabled()) отключают установку хуков при старте — поэтому переключение 0 ↔ ненулевое требует перезапуска, а изменение ненулевого значения нет.

Конфигурация

Шаблон и пользовательская копия

Проектный config.py — шаблон с дефолтами, приложение его не модифицирует. При каждом старте bootstrap.py пересобирает ~/active_time/config.py: структура, комментарии и набор параметров — из шаблона, значения присваиваний верхнего уровня — из существующей пользовательской копии (разбор через ast). Так новые параметры появляются в рабочем конфиге автоматически, а настроенные значения сохраняются. Побочный эффект: ручные комментарии и переменные, которых нет в шаблоне, при пересборке теряются — пользовательский конфиг рассчитан на управление через диалог настроек. Пользовательская копия подключается как модуль config через sys.path. Обратная запись — modules/settings/writer.py: диалог настроек (modules/settings/: каркас в dialog.py, по модулю на вкладку) собирает значения в плоский словарь, write_config_file подставляет их в файл построчными заменами (комментарии и структура остаются; чистая часть — render_config, tests/test_settings_writer.py), apply_runtime кладёт те же значения в модуль config в памяти.

Конвенция hot-reload. Значения, изменяемые через диалог настроек, читаются в коде как config.X (через import config), а не from config import X — иначе имя биндится при импорте модуля и обновления через settings.writer.apply_runtime не применяются до перезапуска. Диалог пишет в config.X напрямую и в файл. Та же конвенция у тем: theme.COLOR_X.

Автозагрузка

Галочка «Запускать при входе в Windows» — единственная настройка вне config.py: modules/autostart.py пишет значение User Active Time в HKCU\Software\Microsoft\Windows\CurrentVersion\Run (ветка пользователя, прав администратора не нужно). Источник истины — реестр: запись можно удалить или выключить в Диспетчере задач, а выключение там пишет флаг в …\Explorer\StartupApproved\Run (нечётный первый байт = выключено), поэтому is_enabled учитывает оба ключа, а set_enabled снимает флаг. Команда — без консоли: pythonw.exe из окружения текущего интерпретатора + main.py, в сборке PyInstaller — сам exe; от рабочей папки приложение не зависит. Галочка отдаётся вкладкой через GeneralTab.autostart() отдельно от values(), диалог после записи конфига вызывает autostart.apply: реестр трогается только при смене состояния или если запись указывает на пропавшие файлы (перенос папки) — рабочую запись другой копии простое «OK» не перебивает. Отказ записи (OSError, например запрет политикой) показывается сообщением, остальные настройки сохраняются.

Темы оформления

Все цветовые параметры обеих палитр — в modules/theme.py. Палитры описывают одни и те же роли (фон, текст, статусные зелёный/жёлтый/красный, подсказки), поэтому новая тема или правка цвета — в одном месте. Модули читают цвета динамически как theme.COLOR_*, поэтому окна, открытые после переключения (set_theme() из диалога), рисуются в новой палитре. Постоянный виджет уже созданными tk-виджетами сам не перекрашивается — после смены темы он пересобирает свою «хромированную» часть (ActivityWidget.apply_theme, зовёт ядро — App._on_settings_saved). Мини-виджеты там же перекрашивают каркас — окно, подпись, крестик (WidgetManager.apply_theme → BaseMiniWidget.apply_theme), а содержимое перерисовывают на ближайшем update(stats), который ядро вызывает сразу: канвы и сетки читают палитру при каждой отрисовке. Цвет текста на полосах мини-виджета «Метрики» выбирается по яркости подложки: палитры инвертированы, и фиксированный белый/чёрный читался бы только в одной теме.

Виджет и метрики

Пакет modules/widget/: app.py — ядро UI (App): корень Tk, общий тикер (500 мс) и раздача данных равноправным потребителям — окну-конфигуратору, мини-виджетам (WidgetManager), трею и звукам: stats раз в WIDGET_UPDATE_INTERVAL (App.refresh, его же зовут после ручного времени и настроек), остаток до неактивности раз в секунду (tick_second), шаг мигания каждый тик (tick_blink — счётчики в заголовке и на мини-виджете мигают в одну фазу); здесь же инструменты (переживают пересборку окна при смене темы), трей и выход. alerts.py — звуковые сигналы (SoundAlerts): норма — один раз на пересечение порога, тиканье — в предупредительной фазе; решаются по данным, а не по тому, что нарисовано, — окно о звуках не знает; проигрыватели передаются в конструктор (tests/test_sound_alerts.py). widget.py — окно-конфигуратор (ActivityWidget: хром, сворачивание до заголовка и в трей, диалоги из тулбара; данные получает от ядра через update/tick_second/tick_blink, применение настроек отдаёт ядру колбэком on_settings_saved),content.py — тело + недельная полоса как одно целое (создаются, прячутся и пересобираются вместе), actions.py — действия меню «Отчёты»/«Помощь» как функции от окна-родителя (тулбар получает их через functools.partial), position.py — позиция окна между запусками, title_bar.py — заголовок с кнопками, drag и метриками, countdown_indicator.py — обратный отсчёт в заголовке: мигание, режим «норма выработана», цвет рамки и уровень прогресса для неё (progress_level) (заголовок делегирует ему свой публичный API), toolbar.py — панель, toolbar_reveal.py — тулбар свёрнутого окна (ToolbarReveal): показан, пока курсор над окном (winfo_containing) или фокус в нём (focus_get), «в нём» — само окно или его потомок по tk-пути, включая диалоги и подсказки; повод для проверки — <Enter>/<Leave>/<FocusIn>/<FocusOut> на окне плюс тик виджета (фокус, ушедший из диалога в чужое приложение, окну событием не приходит); прячется с паузой HIDE_DELAY_MS, чтобы не мелькать; раскрытое меню держит тулбар через WidgetToolbar.menu_open (tk_popup на Windows блокирует до закрытия меню). Раскладку под заголовком собирает ActivityWidget._apply_layout, body.py — метрики строками (каталог метрик и шкалы — в modules/metrics.py и modules/scales.py, см. ниже), day_timeline.py — строка «Таймлайн дня» в теле, week_strip.py — недельная полоса, timeline_cells.py — нарезка ленты дня на ячейки и палитра (общая для тела и мини-виджетов, без tkinter), tray.py — значок (pystray); двойной клик по значку переключает окно конфигуратора (ActivityWidget.toggle_visible: withdrawn — показать, иначе — в трей). win32-бэкенд pystray сам активирует значок по WM_LBUTTONUP, то есть по одиночному клику, поэтому _make_icon_class подменяет его приватный _on_notify: WM_LBUTTONUP глушится, WM_LBUTTONDBLCLK уходит в on_toggle, остальное (правый клик → меню) — в исходный обработчик; create_tray возвращает None, если pystray/Pillow нет или значок не запустился, — приложение работает без трея. Подсказка значка — название с версией и одна метрика каталога (tooltip_text, короткая подпись + render(percent=True)); пересчитывается на каждой раздаче метрик ядром (update_stats) и при выборе в подменю «Метрика в подсказке». Одна метрика, а не набор, — из-за предела подсказки Windows в 127 символов (szTip): длиннее ctypes не обрежет, а упадёт, поэтому текст режется явно. win32-бэкенд pystray собирает меню один раз — после выбора отметку переставляет update_menu(); обработчики пунктов привязывают ключ замыканием, потому что pystray проверяет их число аргументов, notification.py — генерация и проигрывание звуков. Позиция окна сохраняется между запусками; у спрятанного в трей окна — не на выходе (координаты ни разу не показанного окна нулевые), а при отпускании после перетаскивания.

Цветовые шкалы — каждая метрика красится по своей: активность (RECOMMENDED_ACTIVITY_THRESHOLD/MIN_ACTIVITY_THRESHOLD, процент от нормы активности), рабочее время (RECOMMENDED_WORK_TIME_THRESHOLD/MIN_WORK_TIME_THRESHOLD, full_day_time / max_work), свободное время (FREE_TIME_WARNING_PERCENT). Рамка: зелёный при рекомендуемой норме перекрывает красный алерт счётчика, красный перекрывает жёлтый минимального порога; при выключенном WIDGET_PROGRESS_HIGHLIGHT остаются только красные алерты, а зелёным при норме — только заголовок.

Каталог метрик (modules/metrics.py): одна запись Metric на метрику — подписи (в теле, компактная, для одного процента, для галочек настроек; пустые наследуют основные), значение текстом и парный процент как функции от stats, цветовая шкала и флаги WIDGET_SHOW_* тела. Пары «время + процент» — одна метрика: render(stats, value=…, percent=…) даёт «5ч 12м», «5ч 12м (86.6%)» или один процент, прочерк — когда данных нет; color(stats, decimals) сверяет порог с показанным числом. Порядок METRICS — порядок строк тела и галочек настроек, TITLE_METRICS — что можно вывести в заголовок. На каталоге стоят тело, заголовок, вкладка «Метрики» настроек и мини-виджеты «Метрики» и «Отметки времени» (tests/test_metrics_catalog.py). Новая текстовая метрика — запись в каталоге плюс поле в stats. Каталог и шкалы (modules/scales.py) лежат вне пакета widget намеренно: они без tkinter и нужны настройкам, а импорт любого модуля modules.widget.* тянет widget/__init__ → окно-конфигуратор → диалог настроек, и настройки замыкали бы цикл.

Таймлайн дня в теле (day_timeline.DayTimelineRow): строка тела, но не «лейбл + значение», а Canvas-полоса шириной 180 px; тело хранит её отдельно от _metric_labels и прячет/показывает вместе с ними в нерабочий день. Ячейка — пиксель (timeline_cells.cell_kinds), соседние одного вида склеиваются в полосы (cell_runs — им же пользуются полоса «Метрик» и кольцо) и рисуются одним прямоугольником; поверх — отметки целых часов строго внутри отрезка (hour_tick_positions). Подсказка — ui_utils.attach_pointer_tooltip: текст спрашивается на каждом <Motion> и окно едет за курсором. Сверху — полоса под курсором как нарисована (а не сырой отрезок: при пикселе в 3–4 минуты под красным мог бы оказаться 20-секундный зелёный); её границы — timeline_cells.run_bounds: граница ячейки подтягивается к ближайшей настоящей границе отрезка не дальше ячейки, края ленты — первый логин и «сейчас» (последняя полоса — «идёт»). Описания ручного времени — timeline["manual_notes"] из session_monitor.activity.build_timeline. Подпись собирает modules/timeline_hover.py (без tkinter, общий с отчётом): длительность считается по показанным минутам, чтобы сходилась с часами. Ниже черты — прежняя сводка дня (tooltip_text, tests/test_day_timeline.py, tests/test_timeline_hover.py). timeline_cells вынесен из mini/timeline.py намеренно: тело и мини-виджеты пользуются им на равных, а импорт из mini внутри body завязывал бы тело на пакет мини-виджетов. По той же причине шкалы живут в modules/scales.py, а не в body.

Недельная полоса: раскладка дат и источники данных — modules/week_activity.py (без tkinter; build_days — для любого списка дат, ею же пользуется мини-виджет «Тепловая карта»). Прошлые дни — из дневных JSON-отчётов, сегодняшняя клетка — из живой статистики (отчёт отстаёт на checkpoint). Файлы перечитываются на каждом обновлении. Виды клеток: данные есть / рабочий день без отчёта / нерабочий / будущий (tests/test_week_activity.py).

Панель инструментов не знает, что делают пункты меню «Инструменты» — они приходят из реестра modules/tools. Меню «Помощь» открывает документы из docs/ через utility.resource_path, а пункт «Что нового» — окно ChangelogViewer с CHANGELOG.md (см. Документация).

Мини-виджеты

modules/widget/mini/: base.py — базовое окно (поверх всех, без рамки, перетаскивание с любого места, крестик по наведению, ПКМ-меню) и типовой каркас для _build(): канва с подписью caption под ней (_build_canvas, _build_caption) и подгонка высоты канвы под число строк (_fit_canvas_height), ring.py — кольцо-прогресс с общей геометрией и минимальной рисуемой дугой, типы: pie.py (активность), worktime.py, freetime.py, timeline.py, bars.py, marks.py, heatmap.py, countdown.py (фазу счётчика и заполнитель «__:__» берёт у заголовка — countdown_indicator.countdown_phase, GOAL_PLACEHOLDER, поэтому оба счётчика переключаются одинаково). manager.py — создание/удаление/восстановление/persist, widgets_dialog.py — окно управления, options_menu.py — пункты ПКМ-меню по схеме реестра.

Реестр типов

mini/registry.py — единый источник для UI (подпись, схема настроек) и для спавна по строковому типу. Новый тип — одна запись; его настройки описываются декларативно в options, и диалог управления рендерит контролы по схеме, не зная о конкретных типах:

{"key": str, "label": str, "default": value, "choices": [(value, label), ...], "kind": ...}
kind: OPTION_CHOICE (по умолчанию) — радиокнопки, значение — строка;
      OPTION_MULTI — набор галочек, значение — список ключей в порядке choices

Общая опция center («Процент»/«Время») — у всех кольцевых типов. ПКМ-меню строится по той же схеме, активное значение выделено жирным; правая кнопка внутри меню намеренно не выбирает пункт (tests/test_widget_menu.py).

Таймлайн: раскладка по ячейкам

Кольцо шириной 120 px показывает около 300 точек на рабочий день, поэтому круг рисуется не отрезок за отрезком, а по ячейкам: отрезок «первый вход → сейчас» делится на равные ячейки (~2,5 мин), каждая достаётся тому, чего в ней больше (при равенстве — ручному времени). Короткие отрезки округляются до ячейки. Полоса «Таймлайн» в «Метриках» и строка «Таймлайн дня» в теле виджета режутся так же, только на ячейки шириной в пиксель (общий код — widget/timeline_cells.py). Разбивка — из тех же sessions/idle с текущим таймаутом, сумма зелёного совпадает с «Активным временем» без ручных диапазонов; ручное время за пределами отрезка на круг не попадает (tests/test_timeline_arcs.py).

Подсказка при наведении у всех трёх лент одна: timeline_cells.run_caption по ячейке под курсором находит полосу как нарисована (cell_runs), её границы (run_bounds) и подпись (timeline_hover). Различается только то, как точка становится ячейкой: у полос — по x, у кольца — mini.timeline.cell_at, угол atan2(dx, -dy) от 12 часов по часовой (ось y экрана вниз) и только в пределах толщины кольца, чтобы центр с процентом оставался без подсказки. Подсветка — рамка у полос и пара тонких дуг по краям кольца, на теге hover; ячейки по видам мини-виджеты считают при первом наведении после отрисовки. При зажатой левой кнопке (перетаскивание мини-виджета) attach_pointer_tooltip подсказку прячет: <Motion> канвы срабатывает и во время drag окна (tests/test_timeline_hover.py).

Полосы и отметки

«Метрики (полосы)»: заливка подрезается 0–100%, цвет — своя шкала полосы, порядок фиксированный, высота по числу полос (tests/test_metric_bars.py). «Отметки времени» — отдельный тип, потому что у момента нет процента; отметка стоит на месте, меняется только цвет (tests/test_time_marks.py).

«Тепловая карта» (heatmap.py): сетка tk.Label, как в окне тепловой карты, — у каждой клетки своя подсказка без ручного попадания в координаты Canvas. Раскладка (grid_rows: строки по семь, дата или None) и заголовок столбцов (column_weekdays) считаются без tk; в скользящем режиме первая строка добивается None слева, чтобы сегодня стоял последним, а столбцы всё равно соответствовали дням недели. Сетка пересобирается только при смене ключа раскладки (сегодня, период, отсчёт), на обычном тике клетки перекрашиваются. Данные клеток — week_activity.build_days (общее с недельной полосой: сегодня из stats, прошлое из отчётов), цвета, рамка и подсказка — публичные помощники week_strip. До 31 чтения дневных JSON на тик, без кэша — как у полосы, чтобы правка прошлого дня была видна сразу (tests/test_heatmap_widget.py).

Инструменты

Пакет modules/tools/. Расширяется реестром, а не загрузкой плагинов: полноценная система плагинов была бы инфраструктурой ради одной фичи, а PyInstaller плохо дружит с динамической загрузкой модулей. registry.py — TOOL_CLASSES и формат схемы настроек, spec.py — виды контролов (вынесены отдельно, чтобы не было кольца импортов), __init__.py — фасад (создание, пункты меню, обновление настроек, остановка). Инструменты живут в окне-конфигураторе — доступны только когда виджет включён.

От класса инструмента нужно: key, title (заголовок группы в настройках), label (пункт меню), SETTINGS, __init__(root), attach(), refresh() (перечитать настройки после диалога), detach(), menu_items().

SETTINGS = [
  {"key": "имя параметра в config.py", "label": "подпись", "kind": SETTING_BOOL | SETTING_INT | SETTING_TEXT,
   "from"/"to"/"step" (для INT), "width" (для TEXT), "hint": "серая подсказка",
   "validate": fn(value) -> (title, text) | None},
]

Диалог настроек рендерит вкладку «Инструменты», пишет config.py и применяет значения, не зная конкретных инструментов; вкладка не показывается, если ни у одного инструмента нет настроек. Невалидное значение не сохраняется — диалог остаётся открытым с ошибкой.

Блокировка ввода

tools/input_lock/: hotkey.py — разбор комбинации и распознавание нажатия (чистая логика без Windows), blocker.py — фильтр в hook-потоке (проглотить событие или пропустить), overlay.py — плашка, elevation.py — распознавание окна с повышенными правами на переднем плане, controller.py — жизненный цикл: блокировка/снятие, таймер автоснятия, реакция на события сессии, предупреждение об обходе.

Отдельных хуков не ставится: приложение уже держит LL-хуки для учёта активности, и блокировка — тот же хук, который вместо CallNextHookEx возвращает 1. Учёт времени под блокировкой:

  • отсчёт до простоя не замирает — время идёт как при обычном бездействии;
  • проглоченные нажатия отсчёт не сбрасывают: фильтр стоит до учёта;
  • разблокировка комбинацией засчитывается как ввод (нажал человек); автоснятие по таймеру и снятие при блокировке сессии — нет.

Ctrl+Alt+Del и Win+L не перехватываются — обходится только драйвером, а приложение принципиально без прав администратора. Комбинация без модификатора отобрала бы клавишу у всех приложений, поэтому валидатор её отклоняет. При аварийном завершении процесса хуки снимаются вместе с ним.

Ещё одна дыра — UIPI: Windows не вызывает LL-хуки процесса для ввода, адресованного окну процесса с более высоким уровнем целостности (окно администратора, SYSTEM-агент вроде уведомления антивируса). Пока такое окно активно, blocker.input_filter просто не вызывается, и ввод идёт мимо; закрыть дыру можно только правами администратора или подписанным UIAccess-приложением из Program Files. Поэтому её только распознаём: тик контроллера (_TICK_MS = 500 мс) зовёт elevation.elevated_foreground() — GetForegroundWindow → PID → OpenProcess(PROCESS_QUERY_LIMITED_INFORMATION) → RID метки целостности токена (TokenIntegrityLevel) против своего. Процесс, который не открыть или в чей токен не заглянуть (типично для SYSTEM), считается повышенным. Смена состояния уходит в LockOverlay.set_bypassed (красный заголовок «Блокировка не действует» + имя exe) и в лог [LOCK]; снятие блокировки состояние сбрасывает. Плашка при смене ширины центрируется по winfo_reqwidth — winfo_width до перерисовки ещё старая.

Тесты — tests/test_input_lock.py.

Документация

Два документа в docs/, оба HTML — Markdown по умолчанию не открывается почти ни у кого, а браузер есть у всех:

  • docs/user_guide.html — руководство пользователя: только то, что видно в интерфейсе, без имён параметров и модулей;
  • docs/developer_guide.html — этот документ.

Файлы самодостаточные (стили внутри, тёмная тема по prefers-color-scheme), чтобы один файл можно было переслать. Папка поставляется со сборкой (main.spec) и открывается из меню ❓: «Помощь» → руководство, «Техническая документация» → этот файл; путь берётся через utility.resource_path, который в сборке смотрит в sys._MEIPASS. README.md в корне — короткая страница для GitHub со ссылками сюда.

Третий документ — CHANGELOG.md в корне, и он намеренно не HTML: это плоский список строк по версиям, рендерить из него страницу незачем. Пункт ❓ → «Что нового» показывает его своим окном (modules/changelog_viewer.py): os.startfile тут не годится — расширение .md в Windows часто ни к чему не привязано, а собственное окно ещё и рисуется в теме приложения. Разметка не разбирается: из markdown в файле встречаются только # и ##, у них убираются решётки и вешается тег (title / version), остальные строки вставляются как есть. Текст read-only через state=DISABLED — выделение и копирование при этом работают. Файл кладётся в корень сборки datas в main.spec и ищется тем же utility.resource_path.

Документация — часть изменения, а не follow-up: любая доработка обновляет оба документа в той части, которой касается (поведение — в руководстве, устройство — здесь), в том же коммите.

Версионирование и релиз

Версия живёт в version.py (__version__) — единственное место, где её нужно менять. Схема — CalVer ГОД.МЕСЯЦ.НОМЕР:

2026.08.1   первый релиз августа 2026
2026.08.2   следующий релиз того же месяца
2026.10.1   в сентябре релизов не было — это нормально
  • ГОД — четыре цифры, МЕСЯЦ — две с ведущим нулём (чтобы версии сортировались как строки);
  • НОМЕР — порядковый номер релиза внутри месяца, сбрасывается на 1 в начале каждого месяца. Считает релизы, а не фичи: любой выложенный билд увеличивает его на единицу — правило механическое, две сборки не получат одну версию.

SemVer не используется намеренно: внешних потребителей API нет, ломать совместимость не для кого, а «насколько свежая у меня сборка» — вопрос по делу. Версия видна в ❓ → «О программе» и в подсказке трея; в заголовке виджета её нет — он компактный и мигает при простое.

Чейнджлог

CHANGELOG.md в корне — что нового в каждой версии, коротко и по-человечески; номер CalVer сам по себе этого не говорит. Ведётся по ходу работы: каждая законченная доработка (обычно — отдельный коммит) добавляет строку - ... под заголовок ## Не выпущено. Закрывать раздел версией руками не нужно — это делает скрипт релиза, и пустой раздел он не выпускает. История до 2026.09.4 восстановлена по релизным коммитам.

Выпуск релиза

git add .                                        # решаешь, что входит в релиз
python scripts/release.py "week activity strip"  # бамп + коммит + аннотированный тег
git push --follow-tags                           # или сразу флагом --push

scripts/release.py считает следующий номер (тот же месяц — +1, новый — сброс на 1), переписывает __version__, в CHANGELOG.md переименовывает раздел «Не выпущено» в «<версия> — <дата>», коммитит то, что лежит в индексе, плюс version.py и CHANGELOG.md, и ставит аннотированный тег v<версия>. Перед записью проверяет, что версию не бампнули руками, такого тега нет и раздел «Не выпущено» не пуст (кроме --version-only); --dry-run показывает план. Подробности — scripts/release.md. Руками то же самое: поменять __version__, закоммитить, git tag -a v2026.09.1 -m "Release 2026.09.1", git push --follow-tags (обычный git push теги не забирает; git config --global push.followTags true). Тег — шаг, который терялся чаще всего: у релизов 2026.08.6–2026.08.10 тегов не было, ради этого скрипт и появился. Тесты — tests/test_release_version.py.

В Claude Code тот же ритуал целиком — скилл /release (.claude/skills/release/SKILL.md): коммитит незакоммиченные доработки отдельными коммитами, проверяет у них и у всех коммитов с прошлого тега строку в чейнджлоге и правку доков, сверяет main с origin и последний тег с __version__, гоняет тесты, затем release.py --version-only --push и проверяет, что тег доехал до сервера. Необязательный аргумент — описание релиза для заголовка коммита.

Сборка

PyInstaller по main.spec: datas кладёт рядом с исполняемым файлом папку docs/ и CHANGELOG.md, hiddenimports=['pystray._win32'] — потому что pystray грузит бэкенд лениво и PyInstaller его не видит. Сборка в режиме COLLECT (папка dist/main/), консоль включена. build/ и dist/ в git не хранятся (см. .gitignore) — сборка делается локально. Ресурсы в рантайме ищутся через utility.resource_path: от sys._MEIPASS в сборке, от корня проекта при обычном запуске.

.venv\Scripts\python -m PyInstaller main.spec
