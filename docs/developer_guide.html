Окружение и запуск

Ядро (мониторинг сессий и ввода, виджет, отчёты) работает на стандартной библиотеке + ctypes. Внешние пакеты нужны только для значка в трее — pystray и Pillow (requirements.txt). Без них приложение работает, но значка нет: кнопка «свернуть в трей» откатывается к сворачиванию до заголовка, а в консоль выводится подсказка с командой установки для нужного интерпретатора.

Рекомендуемый способ — отдельное виртуальное окружение проекта, чтобы приложение всегда запускалось своим интерпретатором со своими зависимостями:

py -3.12 -m venv .venv
.venv\Scripts\python -m pip install -r requirements.txt
.venv\Scripts\python main.py          # или start.bat

Тесты — pytest, все в папке tests/: python -m pytest tests. Tkinter в тестах не поднимается: тестируется чистая логика (интервалы, раскладки, схемы, разбор комбинаций).

Архитектура и потоки

main.py подключает пользовательский конфиг (bootstrap.setup_user_config() — до любых импортов, читающих config), затем запускает монитор сессий в daemon-потоке SessionMonitor, а в главном потоке — Tkinter-виджет. Если все опции отображения виджета выключены (is_widget_enabled()), монитор крутится в главном потоке без UI.

ПотокЧто делает
главный (Tk)виджет-конфигуратор, мини-виджеты, диалоги, окна отчётов; читает статистику через get_current_stats
SessionMonitorскрытое окно + цикл сообщений Windows: WTS-уведомления о LOGON/LOGOFF/LOCK/UNLOCK (win_events.py)
hook-потокlow-level хуки клавиатуры и мыши с собственным циклом сообщений (events_monitor.py); колбэки максимально лёгкие
timer-поток вводамашина состояний простоя: замыкает гэпы, пишет события, считает обратный отсчёт
checkpointфоновый таймер промежуточного сохранения (checkpoint.py)

Ключевые приёмы:

  • колбэки вместо импортов — events_monitor получает log_event колбэком, чтобы не было кольца импортов;
  • хуки только присваивают time.monotonic() и вызывают CallNextHookEx; весь I/O — в timer-потоке. Атомарность присваиваний float/str между потоками обеспечивает GIL;
  • остановка потоков через threading.Event / request_stop();
  • состояние дня защищено state_lock, которым владеет session.py.

Пакет modules/session_monitor/ собран слоями снизу вверх, импорты строго в одну сторону; внешние потребители импортируют всё из фасада modules.session_monitor, не зная раскладки:

state_store   — state.json и схема записи дня (v2), сериализация интервалов
journal       — строки лога дня: сборка и разбор (чистый текст, без I/O)
activity      — пересчёт активного времени и таймлайна из сырых интервалов
day_report    — мост day_state ↔ дневной JSON-отчёт (запись и чтение прошедших дней)
session       — владелец рантайма (session_start_time, state_lock) и жизненный цикл:
                start/end/checkpoint/recover, log_event
checkpoint    — фоновый таймер промежуточного сохранения
stats         — get_current_stats для виджета
manual_time   — ручное добавление/удаление активного времени
win_events    — WTS-подписка, скрытое окно, цикл сообщений, main()

Модель активного времени

События

В лог дня пишутся события: LOGON, LOGOFF, LOCK, UNLOCK, IDLE (зафиксированный период простоя), MANUAL_ADD_START/MANUAL_ADD_END (ручные диапазоны), SESSION_RECOVERED (сессия дотянута после сбоя).

Схема v2: сырые интервалы

Программа записывает не «активно/неактивно», посчитанное по таймауту, а сырые интервалы: периоды включённой сессии sessions ([start, end]) и гэпы простоя ввода idle ([from, to], без вычета таймаута). Активное время — проекция от них с текущим INPUT_ACTIVITY_TIMEOUT, вычисляемая в момент чтения/записи. Поэтому изменение таймаута пересчитывает весь день, включая прошедшую часть. Старые записи (v1) читаются как раньше: ensure_v2 сохраняет накопленное active_seconds как legacy_base_seconds (за вычетом ручного времени, которое пересчитывается из лога заново).

Ядро — modules/activity_intervals.py, чистые функции без I/O:

неактивность гэпа   = [from + timeout, to]      (None, если гэп короче таймаута)
активное за день    = Σ длительность сессий − Σ неактивность
                      (пересечения обрезаются границами суток [00:00, следующая полночь))

Таймаут — разовая «фора», сдвигающая начало гэпа, поэтому переход через полночь обрабатывается корректно. Пересчёт точен для таймаутов ≥ MIN_IDLE_GAP_SECONDS. Тот же код раскладывает таймлайн дня для круга и полосы «Таймлайн».

Две нормы

Единая точка расчёта — utility.py: get_work_hours(date) (присутствие: WORK_HOURS_BY_DAY с переопределениями из календаря work_calendar.py), get_break_hours(date), get_activity_norm_hours(date) = рабочие часы − перерыв, не ниже нуля; в нерабочий день перерыв не вычитается. Присутствие красится по RECOMMENDED_WORK_TIME_THRESHOLD/MIN_WORK_TIME_THRESHOLD, активность — по RECOMMENDED_ACTIVITY_THRESHOLD/MIN_ACTIVITY_THRESHOLD.

Свободное время

бюджет_rec  = присутствие − норма_активности × RECOMMENDED_ACTIVITY_THRESHOLD / 100
бюджет_min  = присутствие − норма_активности × MIN_ACTIVITY_THRESHOLD / 100
потрачено   = full_day_seconds − active_seconds
остаток     = бюджет_rec − потрачено        (не подрезается нулём, показывается со знаком)

Цвет — по остатку до рекомендуемой нормы (зелёный / жёлтый при остатке ≤ FREE_TIME_WARNING_PERCENT% бюджета / красный при ≤ 0). Кольцо «Свободное время» за 100% берёт бюджет_min, чтобы пустеть непрерывно; при остатке ниже минимальной нормы красным становится трек.

Достижение нормы активности

Прогноз = now + (норма_активности × порог − active_seconds); после взятия порога — фактический момент, вычисленный по тем же интервалам дня, и дальше не меняется. None → «—» (нерабочий день или нулевая норма). Тесты — tests/test_recommended_eta.py.

Усечение процентов

utility.truncate_percent: дробная часть отбрасывается, и с порогами сравнивается то же показанное число — иначе округление вверх давало «80%» жёлтым. Правило действует везде: тело и заголовок виджета, мини-виджеты, тепловая карта, отчёт за период (tests/test_percent_display.py).

Файлы данных и схемы

Всё в LOG_DIR = ~/active_time/.

state.json

Словарь «ключ-дата YYYY-MM-DD → запись дня». Хранит только сегодня и будущие дни: прошедшие вычищает cleanup_old_days после записи отчёта (кроме случая кросс-полуночной незавершённой сессии), и источником истины для них становится дневной отчёт. Запись атомарная — через .tmp + os.replace.

{
  "2026-09-11": {
    "active_seconds": 0,        "session_count": 0,
    "first_login": null,        "last_logout": null,
    "sessions": [{"start": "YYYY-MM-DD HH:MM:SS", "end": "..."}],
    "idle":     [{"from":  "YYYY-MM-DD HH:MM:SS", "to":  "..."}],
    "legacy_base_seconds": 0,   "log_entries": ["..."]
  }
}

Открытая сессия персистится на каждом checkpoint (CHECKPOINT_INTERVAL); при следующем запуске незакрытые из-за сбоя сессии дотягиваются — в лог добавляется SESSION_RECOVERED. При жёстком сбое теряется не более одного интервала checkpoint.

Дневной отчёт <username>_dd.mm.yyyy.json

Формирует modules/report.py (REPORT_JSON_VERSION = 2):

Ручные диапазоны на сегодня и будущее пишутся в state.json; на прошедшие даты — прямо в отчёт (он же создаётся, если активности за день не было). Читают отчёты все окна отчётов, тепловая карта и недельная полоса.

widgets.json

Плоский список записей мини-виджетов: {"id", "type", "x", "y", "opts", "enabled"}. Выключенный виджет не рисуется, но запись с настройками и позицией остаётся (widget_store.py, manager.py).

work_calendar.json

{"YYYY-MM-DD": {"hours": float|null, "note": str}}. hours: ключа нет или null — действует расписание; 0 — выходной; > 0 — переопределённый лимит. Модуль work_calendar.py держит кэш в памяти и зависит только от config.

config.py

Пользовательская копия конфига — см. Конфигурация. Ещё в LOG_DIR лежит сгенерированный WAV звукового уведомления (widget/notification.py).

Мониторинг сессий

Скрытое окно + WTSRegisterSessionNotification — единственный способ узнать о LOCK/UNLOCK/LOGON/LOGOFF без прав администратора. win_events.py регистрирует класс окна (WNDCLASSW, WNDPROC из constants.py), крутит цикл сообщений и транслирует WM_WTSSESSION_CHANGE в операции жизненного цикла из session.py: start_session / end_session / log_event. Остановка — request_stop() посылает WM_QUIT.

Мониторинг ввода

modules/events_monitor.py ставит WH_KEYBOARD_LL и WH_MOUSE_LL в собственном потоке. Колбэк хука только запоминает time.monotonic() и источник (движение мыши учитывается по config.TRACK_MOUSE_MOVE, читается динамически — применяется на лету) и передаёт событие дальше.

Timer-поток раз в секунду сравнивает момент последнего учтённого ввода с текущим: пауза ≥ MIN_IDLE_GAP_SECONDS (5 с, constants.py) по возвращении пользователя замыкается в сырой гэп [from, to] и регистрируется как событие IDLE. Конвертация monotonic → wall-clock идёт через якорь, зафиксированный на старте сессии. При блокировке экрана ввод игнорируется, открытый гэп финализируется. На подсчёт количества сессий это не влияет.

Закрытый гэп виден сразу. В state.json гэп попадает только на ближайшем checkpoint. Живая статистика (stats.get_current_stats) читает state.json, поэтому дополнительно подмешивает гэпы, которые уже закрылись, но ещё не сохранены — events_monitor.peek_idle_gaps(). Без этого простой, только что закончившийся, на минуту исчезал бы из процента активности и с круга «Таймлайн дня» (tests/test_stats_pending_idle.py).

Обратный отсчёт для заголовка и мини-виджета «Счётчик активности» считается здесь же по текущему таймауту — это про «сейчас», а не про запекание истории. INPUT_ACTIVITY_TIMEOUT = 0 отключает установку хуков при старте — поэтому переключение 0 ↔ ненулевое требует перезапуска, а изменение ненулевого значения нет.

Конфигурация

Шаблон и пользовательская копия

Проектный config.py — шаблон с дефолтами, приложение его не модифицирует. При каждом старте bootstrap.py пересобирает ~/active_time/config.py: структура, комментарии и набор параметров — из шаблона, значения присваиваний верхнего уровня — из существующей пользовательской копии (разбор через ast). Так новые параметры появляются в рабочем конфиге автоматически, а настроенные значения сохраняются. Побочный эффект: ручные комментарии и переменные, которых нет в шаблоне, при пересборке теряются — пользовательский конфиг рассчитан на управление через диалог настроек. Пользовательская копия подключается как модуль config через sys.path.

Конвенция hot-reload. Значения, изменяемые через диалог настроек, читаются в коде как config.X (через import config), а не from config import X — иначе имя биндится при импорте модуля и обновления через SettingsDialog._apply_runtime не применяются до перезапуска. Диалог пишет в config.X напрямую и в файл. Та же конвенция у тем: theme.COLOR_X.

Темы оформления

Все цветовые параметры обеих палитр — в modules/theme.py. Палитры описывают одни и те же роли (фон, текст, статусные зелёный/жёлтый/красный, подсказки), поэтому новая тема или правка цвета — в одном месте. Модули читают цвета динамически как theme.COLOR_*, поэтому окна, открытые после переключения (set_theme() из диалога), рисуются в новой палитре. Постоянный виджет уже созданными tk-виджетами сам не перекрашивается — после смены темы он пересобирает свою «хромированную» часть (ActivityWidget._apply_theme). Цвет текста на полосах мини-виджета «Метрики» выбирается по яркости подложки: палитры инвертированы, и фиксированный белый/чёрный читался бы только в одной теме.

Виджет и метрики

Пакет modules/widget/: widget.py — конфигуратор (ActivityWidget), title_bar.py — заголовок с кнопками, drag и счётчиком, toolbar.py — панель, body.py — метрики, week_strip.py — недельная полоса, tray.py — значок (pystray), notification.py — звук. Виджет обновляется раз в WIDGET_UPDATE_INTERVAL, счётчик — раз в секунду. Позиция окна сохраняется между запусками.

Цветовые шкалы — каждая метрика красится по своей: активность (RECOMMENDED_ACTIVITY_THRESHOLD/MIN_ACTIVITY_THRESHOLD, процент от нормы активности), рабочее время (RECOMMENDED_WORK_TIME_THRESHOLD/MIN_WORK_TIME_THRESHOLD, full_day_time / max_work), свободное время (FREE_TIME_WARNING_PERCENT). Рамка: зелёный при рекомендуемой норме перекрывает красный алерт счётчика, красный перекрывает жёлтый минимального порога; при выключенном WIDGET_PROGRESS_HIGHLIGHT остаются только красные алерты, а зелёным при норме — только заголовок.

Недельная полоса: раскладка дат и источники данных — modules/week_activity.py (без tkinter). Прошлые дни — из дневных JSON-отчётов, сегодняшняя клетка — из живой статистики (отчёт отстаёт на checkpoint). Файлы перечитываются на каждом обновлении. Виды клеток: данные есть / рабочий день без отчёта / нерабочий / будущий (tests/test_week_activity.py).

Панель инструментов не знает, что делают пункты меню «Инструменты» — они приходят из реестра modules/tools. Меню «Помощь» открывает документы из docs/ через utility.resource_path (см. Документация).

Мини-виджеты

modules/widget/mini/: base.py — базовое окно (поверх всех, без рамки, перетаскивание с любого места, крестик по наведению, ПКМ-меню), ring.py — кольцо-прогресс с общей геометрией и минимальной рисуемой дугой, типы: pie.py (активность), worktime.py, freetime.py, timeline.py, bars.py, marks.py, countdown.py. manager.py — создание/удаление/восстановление/persist, widgets_dialog.py — окно управления, options_menu.py — пункты ПКМ-меню по схеме реестра.

Реестр типов

mini/registry.py — единый источник для UI (подпись, схема настроек) и для спавна по строковому типу. Новый тип — одна запись; его настройки описываются декларативно в options, и диалог управления рендерит контролы по схеме, не зная о конкретных типах:

{"key": str, "label": str, "default": value, "choices": [(value, label), ...], "kind": ...}
kind: OPTION_CHOICE (по умолчанию) — радиокнопки, значение — строка;
      OPTION_MULTI — набор галочек, значение — список ключей в порядке choices

Общая опция center («Процент»/«Время») — у всех кольцевых типов. ПКМ-меню строится по той же схеме, активное значение выделено жирным; правая кнопка внутри меню намеренно не выбирает пункт (tests/test_widget_menu.py).

Таймлайн: раскладка по ячейкам

Кольцо шириной 120 px показывает около 300 точек на рабочий день, поэтому круг рисуется не отрезок за отрезком, а по ячейкам: отрезок «первый вход → сейчас» делится на равные ячейки (~2,5 мин), каждая достаётся тому, чего в ней больше (при равенстве — ручному времени). Короткие отрезки округляются до ячейки. Полоса «Таймлайн» в «Метриках» режется так же, только на ячейки шириной в пиксель. Разбивка — из тех же sessions/idle с текущим таймаутом, сумма зелёного совпадает с «Активным временем» без ручных диапазонов; ручное время за пределами отрезка на круг не попадает (tests/test_timeline_arcs.py).

Полосы и отметки

«Метрики (полосы)»: заливка подрезается 0–100%, цвет — своя шкала полосы, порядок фиксированный, высота по числу полос (tests/test_metric_bars.py). «Отметки времени» — отдельный тип, потому что у момента нет процента; отметка стоит на месте, меняется только цвет (tests/test_time_marks.py).

Инструменты

Пакет modules/tools/. Расширяется реестром, а не загрузкой плагинов: полноценная система плагинов была бы инфраструктурой ради одной фичи, а PyInstaller плохо дружит с динамической загрузкой модулей. registry.py — TOOL_CLASSES и формат схемы настроек, spec.py — виды контролов (вынесены отдельно, чтобы не было кольца импортов), __init__.py — фасад (создание, пункты меню, обновление настроек, остановка). Инструменты живут в окне-конфигураторе — доступны только когда виджет включён.

От класса инструмента нужно: key, title (заголовок группы в настройках), label (пункт меню), SETTINGS, __init__(root), attach(), refresh() (перечитать настройки после диалога), detach(), menu_items().

SETTINGS = [
  {"key": "имя параметра в config.py", "label": "подпись", "kind": SETTING_BOOL | SETTING_INT | SETTING_TEXT,
   "from"/"to"/"step" (для INT), "width" (для TEXT), "hint": "серая подсказка",
   "validate": fn(value) -> (title, text) | None},
]

Диалог настроек рендерит вкладку «Инструменты», пишет config.py и применяет значения, не зная конкретных инструментов; вкладка не показывается, если ни у одного инструмента нет настроек. Невалидное значение не сохраняется — диалог остаётся открытым с ошибкой.

Блокировка ввода

tools/input_lock/: hotkey.py — разбор комбинации и распознавание нажатия (чистая логика без Windows), blocker.py — фильтр в hook-потоке (проглотить событие или пропустить), overlay.py — плашка, controller.py — жизненный цикл: блокировка/снятие, таймер автоснятия, реакция на события сессии.

Отдельных хуков не ставится: приложение уже держит LL-хуки для учёта активности, и блокировка — тот же хук, который вместо CallNextHookEx возвращает 1. Учёт времени под блокировкой:

  • отсчёт до простоя не замирает — время идёт как при обычном бездействии;
  • проглоченные нажатия отсчёт не сбрасывают: фильтр стоит до учёта;
  • разблокировка комбинацией засчитывается как ввод (нажал человек); автоснятие по таймеру и снятие при блокировке сессии — нет.

Ctrl+Alt+Del и Win+L не перехватываются — обходится только драйвером, а приложение принципиально без прав администратора. Комбинация без модификатора отобрала бы клавишу у всех приложений, поэтому валидатор её отклоняет. При аварийном завершении процесса хуки снимаются вместе с ним. Тесты — tests/test_input_lock.py.

Отчёты

  • modules/report.py — формирование дневного JSON; session_monitor/day_report.py — запись из day_state и чтение прошедших дней обратно.
  • modules/report_viewer.py — окно дневного отчёта: сводка + график по часам. Для v2 график строится из sessions/idle с текущим таймаутом; v1 — по событиям лога.
  • modules/period_report.py — агрегация за период из дневных JSON (без UI), period_report_dialog.py / period_report_viewer.py — диалог и окно. Дни без отчётов пропускаются.
  • modules/month_grid.py — базовый месячный календарь (навигация, сетка, тултипы, подсветка сегодня); наследники переопределяют семантику ячейки: heatmap_viewer.py (цвет по проценту активности) и schedule_calendar.py (календарь рабочего времени, клик → day_schedule_dialog.py).
  • modules/calendar_popup.py — модальный пикер даты для диалогов; manual_activity_dialog.py — ручные диапазоны.
  • «Отчёт за сегодня» перед открытием вызывает checkpoint_session(), чтобы файл отражал сессию до текущего момента; «Последний дневной отчёт» — find_latest_past_report_date.

Миграция старых TXT-отчётов — scripts/migrate_reports_to_json.py (scripts/migrate_reports_to_json.md).

Документация

Два документа в docs/, оба HTML — Markdown по умолчанию не открывается почти ни у кого, а браузер есть у всех:

  • docs/user_guide.html — руководство пользователя: только то, что видно в интерфейсе, без имён параметров и модулей;
  • docs/developer_guide.html — этот документ.

Файлы самодостаточные (стили внутри, тёмная тема по prefers-color-scheme), чтобы один файл можно было переслать. Папка поставляется со сборкой (main.spec) и открывается из меню ❓: «Помощь» → руководство, «Техническая документация» → этот файл; путь берётся через utility.resource_path, который в сборке смотрит в sys._MEIPASS. README.md в корне — короткая страница для GitHub со ссылками сюда.

Документация — часть изменения, а не follow-up: любая доработка обновляет оба документа в той части, которой касается (поведение — в руководстве, устройство — здесь), в том же коммите.

Версионирование и релиз

Версия живёт в version.py (__version__) — единственное место, где её нужно менять. Схема — CalVer ГОД.МЕСЯЦ.НОМЕР:

2026.08.1   первый релиз августа 2026
2026.08.2   следующий релиз того же месяца
2026.10.1   в сентябре релизов не было — это нормально
  • ГОД — четыре цифры, МЕСЯЦ — две с ведущим нулём (чтобы версии сортировались как строки);
  • НОМЕР — порядковый номер релиза внутри месяца, сбрасывается на 1 в начале каждого месяца. Считает релизы, а не фичи: любой выложенный билд увеличивает его на единицу — правило механическое, две сборки не получат одну версию.

SemVer не используется намеренно: внешних потребителей API нет, ломать совместимость не для кого, а «насколько свежая у меня сборка» — вопрос по делу. Версия видна в ❓ → «О программе» и в подсказке трея; в заголовке виджета её нет — он компактный и мигает при простое. Сравнивать версии через version.version_tuple(), а не как строки: при номере ≥ 10 строки врут ("2026.08.10" < "2026.08.9").

Выпуск релиза

git add .                                        # решаешь, что входит в релиз
python scripts/release.py "week activity strip"  # бамп + коммит + аннотированный тег
git push --follow-tags                           # или сразу флагом --push

scripts/release.py считает следующий номер (тот же месяц — +1, новый — сброс на 1), переписывает __version__, коммитит то, что лежит в индексе, плюс version.py, и ставит аннотированный тег v<версия>. Перед записью проверяет, что версию не бампнули руками и такого тега нет; --dry-run показывает план. Подробности — scripts/release.md. Руками то же самое: поменять __version__, закоммитить, git tag -a v2026.09.1 -m "Release 2026.09.1", git push --follow-tags (обычный git push теги не забирает; git config --global push.followTags true). Тег — шаг, который терялся чаще всего: у релизов 2026.08.6–2026.08.10 тегов не было, ради этого скрипт и появился. Тесты — tests/test_release_version.py.

Сборка

PyInstaller по main.spec: datas кладёт папку docs/ рядом с исполняемым файлом, hiddenimports=['pystray._win32'] — потому что pystray грузит бэкенд лениво и PyInstaller его не видит. Сборка в режиме COLLECT (папка dist/main/), консоль включена. Ресурсы в рантайме ищутся через utility.resource_path: от sys._MEIPASS в сборке, от корня проекта при обычном запуске.

.venv\Scripts\python -m PyInstaller main.spec

  • modules/week_activity.py — раскладка недельной полосы (данные, без tkinter)
  • modules/widget/ — конфигуратор: widget.py, title_bar.py, toolbar.py, body.py, week_strip.py, manager.py, widgets_dialog.py, widget_store.py, tray.py, notification.py; mini/ — мини-виджеты и их реестр
